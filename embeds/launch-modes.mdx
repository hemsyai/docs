title: "Launch Modes"
description: "Control what each click opens: Sandbox, Product context, Share, or Flow."
---

Every launcher element decides its own launch mode from the attributes on that exact clicked element. The attributes are the same whether the [Shopify trigger block](/embeds/shopify) emits them from theme editor settings or you write them by hand with the [script install](/embeds/script). This page covers each mode and the order they're resolved in.

Every mode opens the same screen: the visualization on top (or on the left on desktop), a toolbar under it for share and download, and the look as a list of **layers** below it. Shoppers change a layer's color or size, swap its product, add or remove layers, then tap **Update preview** to re-render. Only the starting state differs by mode.

## Resolution order

When a launcher is clicked, Hemsy picks the launch mode by checking, in order:

1. **Share**: the element has `data-hemsy-share`.
2. **Product context**: the element has `data-hemsy-auto-product-context="true"` and a variant is detected on the page.
3. **Sandbox**: none of the above.

`data-hemsy-flow` turns a Sandbox launch into a Flow launch: the look opens on the flow's starter look. On a Product context launch it opens the product [inside the flow](#product-context-in-a-flow) instead. Share launches already have a look, so they ignore it.

`data-hemsy-action` (checkout vs cart) is independent of launch mode. It only changes what the final CTA does. See [Checkout vs Cart](/embeds/checkout-vs-cart).

## Launcher attributes

| Attribute                         | Example      | Description                                                                                                              |
| --------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `data-hemsy-share`                | `"FreyjHz4"` | Opens a previously shared look by its short ID.                                                                          |
| `data-hemsy-auto-product-context` | `"true"`     | Opens with the current PDP variant and renders it right away. Falls back to Sandbox if no variant is detected.           |
| `data-hemsy-flow`                 | `"<flowId>"` | Opens the flow's starter look, or with Product context, the product in its flow step. Ignored for Share. Must be on the clicked element. |
| `data-hemsy-action`               | `"cart"`     | Overrides the final CTA (`checkout` or `cart`) for this launcher only. See [Checkout vs Cart](/embeds/checkout-vs-cart). |

## Sandbox

The default. No launcher attributes needed. The shopper starts on your first model photo with an empty look, then adds items from your full catalog.

```html
<a class="hemsy-launcher" href="#">Design a look</a>
```

## Product context (PDP)

Launch with the product the shopper is currently viewing. Hemsy reads the selected variant from the page (the add-to-cart form or a `?variant=` URL parameter), adds it as the first layer, and renders it on your first model photo without asking for a photo first.

```html
<button class="hemsy-launcher" data-hemsy-auto-product-context="true">
  Try with this product
</button>
```

If no variant can be detected, the launcher falls back to Sandbox mode.

### Product context in a flow

Add `data-hemsy-flow` to a Product context launcher to open the product inside a flow, so shoppers see the rest of the look they could build around it:

```html
<button
  class="hemsy-launcher"
  data-hemsy-auto-product-context="true"
  data-hemsy-flow="YOUR_FLOW_ID"
>
  See it on your bed
</button>
```

- The product goes into the flow step whose scope (collection, tag, category, or metafield) covers it. A sheet set lands in the sheet set step, a throw in the throw step. If it fits several steps, the first one wins.
- The flow's other steps open empty, ready to fill. The flow's starter picks and starter image are skipped.
- The product renders right away on the flow's reference image, the same single render as a plain Product context launch.
- A product no step covers still renders, as an extra layer below the flow's steps.

The same works from the [JavaScript API](/embeds/javascript-api) and [deep links](/deep-links).

## Share

Open a previously shared look by its short ID: the shopper's photo, the render, and every item. Useful for marketing campaigns, emails, or featuring shopper-created looks on your storefront.

```html
<button class="hemsy-launcher" data-hemsy-share="FreyjHz4">
  View Shared Look
</button>
```

Share IDs are generated by Hemsy's in-app Share feature; you don't construct them yourself.

## Flow

Open a flow on its **starter look**: a finished render with one layer per flow step, already filled in.

```html
<button class="hemsy-launcher" data-hemsy-flow="YOUR_FLOW_ID">
  Build a bed
</button>
```

Copy flow IDs from the dashboard's **Flows** page. Each flow sets up:

- **Layers**: one per step, each scoped to a set of products. The shopper swaps a layer's product from that scope. Required layers can be swapped but not removed.
- **Starter picks**: the product and variant each layer opens on.
- **Reference image**: the photo the look renders on.
- **Starter image**: a saved render of the starter picks on the reference image, generated from the flow editor. The shopper sees it the moment the flow opens, with no wait.
- **Shared sizes** (optional): one size picker that sets the size on several layers at once, such as a bed size shared by the sheets, duvet, and coverlet. Hemsy matches each layer's own size names ("Cal. King", "King/Cal. King", and so on) to the shared value.

If a flow has no starter image yet, the shopper sees the reference image with the starter picks listed and taps **Update preview** to render.

## URL auto-open

The embed script watches the page URL for `?share=` and opens the modal automatically on page load:

```
https://your-store.com/?share=FreyjHz4
```

This powers share links: recipients see the look immediately. The parameter is removed from the URL after opening so a refresh doesn't re-trigger it. For SPAs, the script also intercepts `history.pushState` to catch client-side navigations.
